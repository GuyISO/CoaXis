# ドキュメント同期ポリシー

このリポジトリでは、コード変更のたびに関連するドキュメントを同一作業で更新する。 仕様書・README・運用ルールがズレたまま残る状態を許可しない。

## 1. 原則

1. 実装変更を行う前に、影響範囲を確認する。
2. 変更に伴う仕様・責務・運用手順・制約の変化があれば、同一作業でドキュメントに反映する。
3. 仕様と実装がズレていることを発見した場合、実装の優先度より先に文書を修正する。
4. ドキュメント更新が未実施の変更は、完了扱いにしない。
5. 文書は、判断・背景・制約・手順を再開可能な粒度で残しつつ、同じ情報を複数箇所に重複させない。
6. 詳細はカテゴリごとの正本へ集約し、案内ページには目的・重要な方針・正本へのリンクだけを残す。

## 2. 影響範囲の判定

次のいずれかに該当する場合は、必ず関連文書を更新する。

- 3D 表示・入力・イベント・UI の挙動が変わる
- IPC / JSON / DTO / GitHub 上の共有契約が変わる
- Project / solution / directory / build procedure が変わる
- 既存の設計思想や責務分離が変わる
- バグ修正後に再発防止ルールが必要になる

## 3. 更新先の選定

### README

- プロジェクトの構成、責務、開始方法、開発手順を説明する時に更新する
- ルートの [README.md](../../README.md) や各プロジェクトの README を対象にする

### 仕様書

- ユーザー向けの振る舞い、契約、データモデル、責務分離に変化がある場合に更新する
- 代表: [docs/specification/specification_integrated.md](../specification/specification_integrated.md)

### 実装規約

- C# の命名・region・コメント・品質基準に変化がある場合に更新する
- 代表: [docs/rules/implementation-conventions.md](implementation-conventions.md)

### 技術ナレッジベース

- 判断理由、制約、代替案、事故対応、再発防止ルールを残す場合に更新する
- 代表: [docs/rules/technical-knowledge-base.md](technical-knowledge-base.md)

## 4. 実装時の標準フロー

1. 変更の影響範囲を列挙する
2. 影響対象のドキュメントを特定する
3. 実装と文書更新を同一作業で実施する
4. ビルドまたは関連検証を実施する
5. 最後に「変更内容」と「ドキュメント更新内容」を確認する

## 5. 完了条件

以下を満たした場合のみ、変更を完了とする。

- 実装が成功している
- 関連ドキュメントが更新済みである
- 仕様・運用ルール・README の記述に齟齬がない
- 変更の背景と影響範囲が記録されている

## 6. チェックリスト

実装前後に以下を確認する。

- [ ] 変更の影響範囲を特定した
- [ ] 変更対象の仕様書/README/ルールを決めた
- [ ] 同一作業でドキュメント更新を行った
- [ ] 既存の記述と矛盾していない
- [ ] 情報を失わずに重複を削減し、詳細は正本へ集約した
- [ ] 必要なら再発防止ルールを追記した
- [ ] 関連テストまたはビルドを実行した

## 7. 例外ルール

以下は例外扱いとしない。

- 「後でまとめて直す」
- 「コードだけ修正して、あとで仕様書はやる」
- 「README は気が向いたときに直す」

このリポジトリでは、ドキュメント同期は開発の必須工程である。
